## Escopo

Pode alterar: `prisma/schema.prisma`, `prisma/seed.ts`.
Pode criar: novas migrations com `npx prisma migrate dev --name <descricao>`.
Não toca em: `src/app/`, `src/lib/prisma.ts`, Route Handlers.

## Checklist (critérios mensuráveis)

### Tipos de coluna
- `timeCasa String`, `timeFora String` — `String` sem `@db.VarChar(n)`: usa `text` no Postgres (sem limite). Para nomes de times, `@db.VarChar(100)` é mais adequado — adicionar se o projeto tiver restrição de comprimento. Reportar sem aplicar (decisão de produto).
- `golsCasa Int @default(0)`, `golsFora Int @default(0)` — correto. Verificar se `Int` (32 bits, max 2.147.483.647) é suficiente — sim para placar de futebol.
- `fase String` — sem enum Prisma; valores válidos são controlados pelo zod no handler. Consistente com a estratégia do projeto. Reportar como alternativa: `enum Fase { ... }` no schema para garantia no banco.
- `dataJogo DateTime` — correto; armazenado como `timestamp` no Postgres.
- `createdAt DateTime @default(now())` — correto.

### Nullability
- Todos os campos do model `Jogo` são NOT NULL (sem `?`). Verificar se `golsCasa` e `golsFora` devem ser nullable (jogo ainda não realizado) — atualmente têm `@default(0)` que mascara jogos não realizados como 0×0. Reportar como decisão de modelagem sem corrigir.

### Constraints e unique
- Sem `@unique` em nenhum campo além de `id @id`. Verificar se faz sentido unicidade em `(timeCasa, timeFora, dataJogo)` — duplas podem se enfrentar mais de uma vez no torneio, portanto sem unique. OK.
- Sem `@relation` — model sem relacionamentos por enquanto. Correto para o escopo atual.

### Integridade referencial
- Não há relações entre models — sem risco de foreign key violação. OK.

### Consistência schema.prisma × migrations × seed

**Schema vs migration:**
- Ler `prisma/migrations/20260809174513_init/migration.sql` e confirmar que os tipos SQL batem com os tipos Prisma:
  - `id SERIAL PRIMARY KEY` ou `INTEGER GENERATED BY DEFAULT AS IDENTITY` → corresponde a `Int @id @default(autoincrement())`.
  - `timeCasa TEXT NOT NULL`, `timeFora TEXT NOT NULL` → `String` sem `?`.
  - `golsCasa INTEGER NOT NULL DEFAULT 0`, `golsFora INTEGER NOT NULL DEFAULT 0` → `Int @default(0)`.
  - `fase TEXT NOT NULL` → `String`.
  - `dataJogo TIMESTAMP(3) NOT NULL` → `DateTime`.
  - `createdAt TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP` → `DateTime @default(now())`.
- Se qualquer campo divergir (ex: schema diz `@default(0)` mas migration não tem `DEFAULT 0`), reportar e criar migration corretiva.

**Schema vs seed:**
- `prisma/seed.ts` insere campos: `timeCasa`, `timeFora`, `golsCasa`, `golsFora`, `fase`, `dataJogo`. Verificar que todos os campos NOT NULL do model estão presentes no seed. `createdAt` tem `@default(now())` — correto não incluir no seed.
- Verificar que `dataJogo: new Date('...')` nos 8 registros do seed são datas ISO válidas.

**Seed ainda roda limpo:**
- Executar `npm run seed` e verificar saída. Se falhar, reportar o erro exato e propor correção.

### generator e datasource
- `generator client { provider = "prisma-client" output = "../src/generated/prisma" }` — Prisma 7, correto.
- `datasource db { provider = "postgresql" }` — sem `url` (configurado via `prisma.config.ts`) — correto para Prisma 7.

## Limite (só reportar, não corrigir)

- Qualquer alteração em `src/app/` ou Route Handlers.
- Performance de queries (Hulk).
- Validação de input no handler (Capitão América).
